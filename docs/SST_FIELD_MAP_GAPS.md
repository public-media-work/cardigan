# SST field map — gaps

Companion to `config/sst_field_map.json`, which holds the mapping itself as data.
This file answers questions 3 and 4 of the "Map every deliverable to its AirTable
SST field" ticket, on the map *Kristian ships an IWP episode end-to-end, web-only*.

**Method note.** The mapping is derived from code — `WRITABLE_FIELDS` carries real
AirTable field ids, so the eight writable fields are confirmed. **G3 was closed
separately by a live, read-only schema read** (2026-08-28, AirTable Meta API, 248
fields on SST) plus a content sample of every populated `Platform Notes` value.

---

## G1 — Two producers compete for `General Keywords/Tags`

`seo.md` emits two separate 15–20 item lists:

1. The **Keyword Strategy** tiers — Primary, Secondary, Long-Tail, Location.
   `config/house_style.yaml` (line 330) says *"Aim for 15-20 total keywords across
   the SEO Keywords section above"*, which reads as the flattened union of those tiers.
2. A distinct **"YouTube Tags (15–20 recommended)"** block.

`house_style.yaml` sets `keywords: {count: {min: 15, max: 20}}` — one budget, and
both candidates match it, so the count can't disambiguate them.

**Nothing in the prompt or the config says which list lands in the field.** Whichever
one doesn't win has no AirTable target at all.

**Not resolved here** — this is a definition question and belongs to *Define the item*.
Flagging both candidates is the deliverable.

## G2 — `Social Media Description` is writable *and* read as ground truth

This is the sharpest finding, and it is a live hazard rather than a missing feature.

- It sits on the **write allowlist** (`fldntHlzk6PfIT5k2`), so `commit_sst_edits`
  can write it today.
- **No pipeline phase produces it** — nothing can fill it.
- Both `analyst.md` and `formatter.md` read it as the **authoritative** source for
  who appears in an episode:

  > *"The `Social Media Description` field often lists the specific reporters/hosts
  > for each episode … These are authoritative sources for speaker identification."*
  > — `prompts/analyst.md`

  > *"Cross-reference ALL speaker names against SST data — The `Social Media
  > Description` field often lists the specific reporters/hosts … These are
  > authoritative; caption text is not."*
  > — `prompts/formatter.md`

So a write to this field doesn't just overwrite a producer's copy — it corrupts the
input the pipeline uses to identify speakers on **every subsequent run** for that
episode. The damage is silent and compounding.

**Recommendation:** reclassify to `human_authoritative` and drop it from
`WRITABLE_FIELDS` until a producer exists and the speaker-identification role is
moved somewhere else. It is currently the only allowlisted field the pipeline also
consumes as truth.

## G3 — The platform-notes field exists, and it is already occupied

**Closed 2026-08-28 by a live schema read.** The earlier code-only audit concluded
the field didn't exist. That was wrong in an instructive way: it doesn't exist *in
Cardigan's code*, but it very much exists in AirTable.

**The field:** `Platform Notes` — `fldcZgr4ZZTSFR2TE`, type **`richText`**. Long-text,
so a composite is viable.

**A related trap:** the SST field literally named `Transcript` (`fldmWY1YglRIpbF2E`)
is a **date**, not a link. There is no dedicated URL field for a transcript link
anywhere in the 248. `Platform Notes` is the only viable home for it.

### It is not an empty field

Sampling all 69 records with a populated `Platform Notes`:

| | count |
|---|---|
| populated records | 69 |
| **human free prose, no machine marker** | **45** |
| carrying pbswi's `AUTO-GENERATED` header | 24 |
| already containing chapter timestamps | 8 |
| containing a URL | 9 |
| Inside Wisconsin Politics (`6POL`) | 25 |

Two things follow.

**Chapters are already being written here** — 8 records carry exactly the `0:00 Intro`
/ `0:17 Mail-in voting restrictions` shape the `timestamp` phase emits. The pattern
Cardigan would introduce is one somebody is already producing by hand.

**Humans are the majority holder.** 45 of 69 values are operational prose with no
marker — e.g. *"Streaming to Education YouTube channel. Live is already scheduled
&lt;youtube.com/live/…&gt;"*. **A blind field write destroys that.** The real
clobbering risk was never chapters-versus-transcript-link; it is machine-versus-human,
and the human side is two-thirds of the field.

There is also a *second* machine writer: pbswi's `sst-batch-create.py` stamps
`AUTO-GENERATED by sst-batch-create.py | run <id> | <timestamp>`.

### Format decision — an owned block, never a whole-field write

Cardigan writes **only** between its own markers and preserves every byte outside them:

```
--- CARDIGAN AUTO START ---
0:00 Intro
0:17 Mail-in voting restrictions
Transcript: <link>
--- CARDIGAN AUTO END ---
```

- **Both markers present** → replace only what lies between them.
- **Markers absent** → append the block after existing content, separated by one blank line.
- **Exactly one marker present** (a human deleted the other) → refuse and surface it for a
  human. Appending would leave an orphaned or duplicate block.
- **Never** replace the field wholesale, and never write it from a value the client
  merely read earlier — a stale read-modify-write loses whatever a human typed in between.
  AirTable has no compare-and-swap, so "fresh" means the `commit_sst_edits` mechanism:
  re-fetch immediately before the PATCH and abort if the field changed since the
  proposal. That narrows the race window; it does not close it.
- **Verify the round trip.** `richText` is markdown-flavoured: a `---` line can render as a
  rule or a setext underline, and AirTable may re-escape or re-wrap lines. The first
  implementation must write a block, read it back, and confirm the markers survive
  byte-for-byte. Marker matching should tolerate whitespace and escaping changes rather
  than assume an exact string.

**One writer, not two.** The transcript link and the chapters have independent
producers — `formatter` (required) and `timestamp` (optional, 10-minute threshold) —
which would race for the same block if each wrote on completion: whichever finished
second would replace the block and erase the other's contribution.

So **phases never write AirTable.** The block is assembled and written **once, by the
publish step**, from whatever approved items exist on the job at that moment. A job
with no chapters (short content, `timestamp` never ran) simply publishes a block
without a chapter list; adding chapters later is a re-publish, which rewrites the whole
block from current job state and is therefore idempotent. This also matches the map's
stage 5 — publish is a single universal action, not a per-phase side effect.

This mirrors the `AIRTABLE_SYNC_START` / `AIRTABLE_SYNC_END` owned-region convention
already used in pbswi's `sync_airtable_to_obsidian.py`. Plain-text markers rather than
HTML comments, because AirTable `richText` renders comments literally.

### Still blocked on the base owner

`Platform Notes` as a home for automation stamps is **provisional**. pbswi issue
[#142](https://github.com/public-media-work/pbswi/issues/142) — *"Confirm with Lisa:
OK to use SST 'Platform Notes' for automation metadata stamps?"* — was **open and
untouched from 2026-07-02** when this audit was taken (2026-08-28). **Update 2026-10-21:**
on 2026-09-01 the field question was answered there (`Platform Notes` is a Digital Team
field, already used for automation timestamps and chapter lists). #142 stays open pending
the wider AirTable write-posture conversation with the base owner, tracked with the
conditions on Cardigan's SST write path in
[pbswi-ops#9](https://github.com/public-media-work/pbswi-ops/issues/9). `AIRTABLE_SAFETY.md` §3a is explicit that the field
choice is *"pending the base owner's (Lisa's) confirmation … the reason the original
`Notes` field was renamed to `Promo Notes` is unknown."*

So Cardigan writing here would be a **second** automation on a field whose automation
use the base owner has not yet blessed. The format above is ready; shipping it should
wait on #142, or ride along with it.

**Not an authorization.** `target_identified_pending_authorization` in
`config/sst_field_map.json` means the field is identified, nothing more. `Platform Notes`
is not in `WRITABLE_FIELDS`, and adding it is a separate, gated change to the
`propose → review → commit` allowlist that needs explicit approval.

## G5 — Cardigan bypasses the SST write-safety layer entirely

Found while closing G3, and larger than the mapping question.

`AIRTABLE_SAFETY.md` §3 classifies **Single Source of Truth as read-only, technically
enforced**: pbswi's `airtable_writer.py` raises `AirTableSafetyError` on any write, and
writes require an explicit `allow_tables` override *plus documented user authorization*.

The **one** sanctioned bulk path is the templated batch create in §3a — and condition
**C3 is create-only**: *"It never updates or deletes an existing SST record — overwrite
is impossible by construction, not just by policy."*

**Cardigan's entire publish path is an update to existing SST records**, and
`patch_sst_record` (`mcp_server/server.py`) PATCHes AirTable directly with the API key.
It does not route through `airtable_writer.py`, so it gets:

- no table allowlist check
- no rollback line in `~/.airtable-rollbacks/`
- no collision guard

The eight-field `WRITABLE_FIELDS` allowlist is a real control, but it is Cardigan's
own — it is invisible to, and unenforced by, the org's safety layer. `airtable_reconcile.py`
will see these as "Unscoped SST writes."

**This is not a blocker to discover later.** The map's destination is a producer
publishing to AirTable from a browser; that is precisely the update path the safety
contract reserves for documented authorization. Worth resolving deliberately —
either Cardigan adopts `airtable_writer.py` (gaining rollback and the allowlist), or
the publish path gets its own documented authorization with an equivalent rollback
trail. Either way it is a decision, not an implementation detail.

## What this means for the item model

- **5** deliverables are publishable end-to-end today.
- **1** is a hazard to be removed from the allowlist (G2).
- **2** are inert allowlist entries (`Social Media Tags`, `Facebook Description`).
- **1** producer is genuinely stranded with no target at all (YouTube Tags — and only because it loses the G1 contest).
- **2** producers (transcript link, chapters) have a confirmed target in `Platform Notes`, blocked not by mapping but by authorization (G3, G5).
- **1** producer (`Quality Score`) is correctly context-only.

The item primitive — *proposed value, current AirTable value, status* — needs a
fourth axis these gaps expose: **whether the item can be published at all.** An item
with no target field, or one whose field is human-authoritative, is not merely
"not yet approved" — it is unpublishable, and the approval surface should say so
rather than offering an approve button that silently does nothing.
